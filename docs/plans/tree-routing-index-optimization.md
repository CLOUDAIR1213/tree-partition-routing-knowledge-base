## 1. 目标与文档定位

### 3.3 用户问题的定位步骤

后续收到失败案例时，按同一问题逐项记录：原问题、自动或手动模式、实际路由、预期文档/章节、实际回答与引用。先确认预期内容已解析且 ready，再核对分区与子查询，随后检查候选分数、过滤原因和最终上下文，最后检查回答生成。

手动选中预期分区后能命中，只能提示自动路由可能有问题；手动仍不命中，应继续检查解析、索引一致性、召回与阈值，不能直接归咎于模型。

## 4. 第一阶段：修复检索正确性

### 4.1 明确索引状态

IndexRegistry 应明确区分“加载失败”“可用但为空”“可用且有数据”。search、verify、verify_absent 和管理操作统一检查状态，不能用空结果或验证成功代表索引不可用。

加载失败返回现有 `INDEX_NOT_READY` 503；合法空索引才返回空候选。任一必需分区不可用时，保持当前失败关闭策略，不能当作全部内部无证据去联网。健康信息应反映同一状态来源，安全错误不得包含路径、模型密钥或底层堆栈。

新增隔离用例：一个分区加载异常，其他分区正常；失败分区聊天返回 503，Answer/Search Provider 均不调用；合法空分区正常返回无证据。

### 4.2 有界补充召回

区分 `candidate_k` 和 `final_k`。建议首轮 candidate_k 为 final_k 的若干倍，具体倍率作为待校准参数；第一轮仍使用现有向量分数门槛。

处理顺序：候选格式校验 → 分数有效性检查 → Chunk ID 去重 → SQLite 批量读取 → 状态/归属检查 → 分数门槛 → 保留最终结果。分区不匹配继续触发现有隔离错误，不能悄悄转成跨区证据。

有效结果不足且候选可能未耗尽时，扩大查询 limit，排除重复 ID 后继续，直到满足 final_k、候选耗尽或达到硬预算。若适配器支持可靠分页再使用分页；不得假设当前接口已支持 offset。连续两轮没有新 ID 时停止，避免死循环。

达到预算但不足时，诊断中标记“搜索预算耗尽”；对外只能说“已检索范围内没有足够依据”，不能声称全库绝对不存在答案。NaN、Infinity 或无法解析的分数不得作为有效证据。

### 4.3 一致性与并发补强

先提供只读诊断，比较 SQLite 中 ready Chunk 集合与索引中的 ID/分区集合，分类记录缺失、孤儿、分区错误和内容版本不一致。检查不执行删除或补写。

补偿成功的定义应包含删除后缺失验证；验证失败时明确记录补偿失败，不只以 delete 未抛异常认定成功。普通 ID 存在校验与持久化回读验证分开：前者用于请求内检查，后者用于隔离索引适配测试和后续版本发布检查。

读写并发先建立可重复的适配层测试。若同一实例不能安全并发读写，第一版使用同一分区锁包围查询与修改，后续再评估快照读取。不能跨越 await 持有线程锁；多分区操作若需要同时加锁，必须固定加锁顺序。

## 5. 第二阶段：诊断与召回质量优化

### 5.1 一次请求的诊断记录

建议在本地诊断工具中按 request_id 输出以下信息，默认仅保留本次内存结果：

| 阶段 | 信息 | 用途 |
| --- | --- | --- |
| 路由 | 安全处理后的问题、子查询、分区、后续节点路径、路由原因码 | 判断选区与改写是否正确 |
| 索引 | 版本、加载状态、查询次数、候选数 | 判断是否搜索了预期索引 |
| 候选 | Chunk ID、文档、来源通道、原始分数/名次 | 找出正确证据是否被召回 |
| 过滤 | below_threshold、missing_metadata、not_ready、duplicate 等 | 解释丢失位置 |
| 上下文 | 最终 ID、邻接补充 ID、预算截断原因 | 区分召回成功与上下文遗漏 |
| 回答 | 覆盖事项、缺证事项、最终引用、降级原因 | 判断生成阶段是否出错 |
| 耗时 | 路由、召回、补充召回、重排、Answer | 分离性能瓶颈 |

诊断不得返回密钥、服务器路径、未审核正文或其他分区正文。当前没有认证，首版优先本地工具，不新增公开管理诊断接口。保存问题或证据正文应由明确的调试操作触发，并说明保存位置与清理方式。

### 5.2 召回与排序

先保留纯向量基线，再按可关闭的独立改动增加关键词通道、名次融合和重排。所有通道必须限制在获准分区及节点范围内，融合不能突破范围。

关键词通道重点验证产品名、错误码、制度名称和精确字段。中文切词与英文符号保留需要专门用例，不能假设默认全文检索分词直接适用。存储适配选择应在本地依赖与数据规模确认后决定。

建议使用基于名次的融合，避免直接相加不同通道或不同分区的原始分数。向量阈值只适用于向量分数；融合分数、重排分数分别校准，不能统一沿用 0.5。无重排服务时回退到已验证的融合或向量排序，不能导致越区或无限等待。

### 5.3 分块与上下文

保留原文位置和稳定 Chunk 标识，检查长表格的表头、列表前提、例外条款是否被拆离。当前分块计数是启发式 token 计数，模型实际输入截断风险需用本地已安装模型配置核实。

召回命中后，可受预算约束地补充同一文档相邻 Chunk 或所属章节内容；补充内容也必须 ready、同分区且在允许范围内。诊断区分“直接命中”和“上下文补充”，所有可被引用的补充内容进入同一个证据白名单。

更改分块规则不能直接覆盖现有 Chunk ID 与引用；应通过文档修订/索引版本迁移处理。第一轮召回优化不同时调整全部分块参数，以免无法归因。

## 6. 第三阶段：树状知识模型

### 6.1 建议结构

```text
知识根节点
├─ 财务 finance
│  ├─ 费用报销
│  └─ 预算与付款
├─ 人事 hr
│  ├─ 公司基础信息
│  └─ 员工制度
└─ 技术 tech
   ├─ 账号与访问
   └─ 部署与故障
       └─ 文档 → 章节 → Chunk
```

上图是建议分类示例，不能作为当前文档实际归属。主题目录树与文档章节树应区分：主题节点用于缩小业务范围，文档/章节用于证据组织，不为每个 Chunk 创建独立 txtai 实例。

首版保留三个物理分区索引，在其中增加节点元数据与受约束检索能力。每个主题节点不单独维护物理索引，避免大量小索引带来的加载、锁和迁移成本。节点范围必须在候选检索阶段有效约束；若底层不支持，不能仅靠全分区 top-k 后过滤来冒充可靠的节点检索。

### 6.2 建议数据对象

| 对象 | 关键内容 | 约束 |
| --- | --- | --- |
| knowledge_nodes | 稳定 ID、parent_id、所属分区、名称、说明、状态、排序、树版本 | 禁止环、孤儿、跨分区挂接；根节点类型受约束 |
| 文档节点归属 | document_id、node_id、审核记录 | 首版文档唯一主题归属，节点分区必须等于 confirmed_partition |
| 文档章节结构 | 文档 ID、章节 ID、父章节 ID、标题、原文顺序 | 与主题树分开；重复章节名仍可区分 |
| Chunk 节点元数据 | 文档归属节点、章节标识、内容版本 | 不改变 SQLite 正文的权威地位 |
| index_generations | 版本、模型标识、分块版本、树版本、数据水位、状态 | 一次请求固定使用兼容的数据与索引版本 |

数据模型是逻辑建议，是否独立建关联表应在迁移实现时确定。当前 SQLite 仅 create_all，新增 Schema 必须引入显式版本迁移与失败恢复，不能依赖启动自动补列。

首版保留“一文档一分区一主题”的审核约束。跨主题材料先归较宽的父节点或拆分上传；Chunk 多主题、多分区归属不在首版范围。主题树的父节点允许直接挂文档，遍历检索必须包含这些直接内容，不能只搜索叶子。

### 6.3 节点管理规则

新增/改名由维护者操作，内容建议只辅助审核。禁用或删除有文档/子节点的节点前必须完成归属处理；默认拒绝级联删除。跨分区移动通过文档迁区流程逐项处理，不能只修改 parent_id。

同分区节点移动也会改变路由范围，应作为新树版本发布。旧版本尚在服务请求时保持可读，防止路径已变但候选仍按旧范围返回。公司基础信息仍遵循现行 hr 约定，树化本身不改变该业务规则。

## 7. 第四阶段：逐层路由与证据回答

### 7.1 路由过程

1. 沿用输入安全检查；手动分区优先，自动根路由仍最多选择两个分区。
2. 为每个事项生成保留关键实体的子查询，固定本次树/索引版本。
3. 在允许分区中读取当前节点的有效子节点说明与内容覆盖信息。
4. 选择有预算的候选分支，逐层下降；支持停留父节点搜索其子树和直接内容。
5. 合并选中范围，去除祖先与后代造成的重复，进行范围内召回与重排。
6. 检查每个事项的证据充分性；无足够依据时执行受控回退或澄清。
7. 生成回答并返回实际搜索范围、引用和安全的路径解释。

节点说明由维护者确认或从已审核内容生成并审核，不能让待审材料改变路由。路由器输出节点 ID 后须本地校验存在性、有效状态、父子关系和分区；模型不能通过任意 ID 扩大检索范围。

### 7.2 回退与预算

不采用每层只选唯一分支且不可回退的硬裁剪。允许保留少量候选路径，但分别设置最大深度、每层分支数、总叶范围、总候选数、模型调用数和总耗时上限。

自动主题路由无证据时，可在已选分区内回到父节点扩大范围，并记录回退原因；不能访问第三个分区。将来若用户显式指定节点，该节点应作为硬范围，扩大到父节点需要用户重新选择，不能静默扩张。

当前 Router 没有经过校准的置信度，不把模型自报 confidence 当概率。第一版使用结构校验、候选歧义、证据覆盖和预算规则决定停留、回退或澄清。

联网依然要求当前请求显式授权、所有必需内部查询成功且无可用证据、通过低风险资格检查。索引故障、预算耗尽导致的不完整检索、路由澄清不得被等同于已确认的内部无证据。

### 7.3 证据充分性与答案

在引用白名单之外增加按事项的证据状态：可支持、部分支持、无支持。建议 Answer 结构化返回事项和对应证据 ID，由服务端据此形成部分回答或拒答；具体字段在 Schema 中确定。

结构合法只是第一道检查。金额、期限、审批角色、条件等关键事实必须能在引用证据中找到支持；冲突事实应展示冲突并要求确认，不能根据相似度猜测哪个版本有效。独立模型校验可以作为后续选项，但也不等同于事实证明，仍需人工黄金案例检验。

抽取式降级明确显示证据摘录和缺失事项，不能仅因有任意命中就宣称已经完整回答。召回、充分性判断和最终文案分别记录，方便定位失败阶段。

## 8. API、界面与兼容策略

### 8.1 契约演进

| 范围 | 建议变化 | 兼容要求 |
| --- | --- | --- |
| ChatRequest | 后续可增加节点范围选择 | 旧 partition_hint 继续有效；两者冲突必须拒绝 |
| ChatResponse | 可选路由路径、证据状态和版本标识 | 保留 searched_partitions 与 citation 分区约束；旧客户端可继续消费 |
| 文档审核 | 节点归属确认 | 首版旧请求可映射到对应分区根，不能自动猜测主题 |
| 文档详情/目录 | 节点路径、节点筛选 | 保留原状态/分区筛选和 Chunk 原文顺序 |
| 节点管理 | 树读取、维护与版本发布能力 | 未实现前不写成现有端点；管理写接口不随诊断默认暴露 |

不直接扩充 Partition 枚举为所有主题；根分区隔离与业务主题分类分别建模。新增错误码、可空字段和历史快照兼容必须一起检查。版本化 localStorage 读取器应接受符合既定旧版本契约的历史消息，不能让新增字段使全部历史丢失。

正式更改以 FastAPI Schema 为源，生成 `contracts/openapi.json` 与 `frontend/src/api/generated.ts`，同步 API Client 运行时校验。先解决锁定依赖环境，再判断本次发现的 OpenAPI 差异是否需要修复，不能手工抹平生成文件。

### 8.2 界面变化

知识库目录增加主题树筛选和面包屑，区分“节点直接文档数”与“子树总数”。审核页展示建议节点但要求人工确认；迁移来的旧文档显示在分区根，不显示未经审核的主题精确归属。

聊天保留自动/手动分区入口，路径与实际搜索范围可折叠展示。普通用户看“在哪些范围找到依据、哪些事项缺少依据”；分数、过滤计数和模型版本留在本地诊断视图，避免把实现细节塞入日常问答。

错误文案区分“索引暂不可用”“已检索范围无依据”“部分事项无依据”“回答生成失败”，不能全部显示为知识库没有内容。

## 9. 存储迁移、发布与回滚

本节仅为未来迁移设计，不授权当前任务修改运行数据。普通开发验证只使用临时库和隔离索引。

### 9.1 迁移顺序

1. 固定代码、依赖和数据基线，执行只读清点并记录数量与异常。
2. 设计并验证 SQLite 版本迁移，在临时副本演练前进、失败中断与回滚。
3. 为旧文档建立保守映射：保留最终分区，先归分区根；主题细分等待审核。
4. 在独立候选目录构建新索引版本，记录模型、分块、树版本及完整数据清单。
5. 验证 ID、正文摘要校验值、归属、数量，以及关闭后重新加载的可读性。
6. 明确最终切换窗口。首版采用短暂冻结审核、迁区、删除等写操作，固定数据水位后构建/校验最终版本；冻结期间旧索引继续读服务。
7. 新版本就绪后发布活动版本指针；新请求使用新版本，正在执行的请求保留旧版本引用。
8. 解除写冻结前确认数据库、树和索引的版本组合兼容，保留回滚记录。

首次切换可以接受明确的维护窗口，不实现未经验证的双写。若日后要求持续写入，必须另建变更日志、追赶与幂等应用机制，不能在构建期间漏掉新增或删除。

### 9.2 回滚边界

切换前失败直接丢弃候选版本，不修改活动版本。切换后但尚未接受新写入时，可切回匹配的旧版本。新版本已经接受写入后，不能只切回旧索引，否则会丢失可检索新增内容或恢复已删除内容；需冻结写入，重放变化或恢复经确认的一致快照。

旧数据库 Schema 的兼容窗口必须事先定义。索引版本和数据库迁移不是同一个原子事务，应有恢复记录标明最后完成步骤。旧版本清理须等到回滚保留期结束且没有活跃请求引用；清理属于独立维护操作。

## 10. 验证方案与验收标准

### 10.1 代码健康与契约检查

第一阶段使用临时 SQLite、Fake Provider 和真实 IndexRegistry 包装受控底层替身，直接覆盖生产注册表控制流，不能仅测试 FakeIndexRegistry 自己。

| 用例 | 必须结果 |
| --- | --- |
| 加载失败与合法空索引 | 前者 503，后者正常无证据；失败不调用联网 |
| 前 k 条无效，后续存在有效候选 | 在预算内补足并保持排序，无重复引用 |
| 分区或节点越界 | 阻断；不进入 Answer、不进入联网 |
| 非法分数、重复结果、反复同一批候选 | 安全过滤并有界停止 |
| 写入失败、删除补偿未清干净 | 不标 ready，正确记录补偿失败 |
| 树环、孤儿、禁用节点、父节点直接文档 | 拒绝非法结构；合法父节点内容可召回 |
| 自动树回退与手动节点范围 | 自动回退不越根分区；手动不越指定子树 |
| 版本切换、中断与重启 | 请求使用一致版本，失败可恢复 |
| API 与历史会话 | 生成契约一致，旧兼容请求/历史可读取 |

真实 txtai 的小型持久化适配测试应只用临时目录与已存在的本地模型，禁止隐式下载大型模型。依赖或模型缺失要明确跳过，不算通过。不得运行 broad E2E、批量 seed 或质量 benchmark 来代替这些定向测试。

### 10.2 质量评测设计（待单独确定执行范围）

先建立人工核对的黄金样本：每例包含问题、模式、预期分区/主题范围、可支持的文档与证据集合、必要事实、无证据或部分证据状态。每条预期证据必须真实存在，不能根据模型回答反向修改答案。

数据按主题和原始事实分组划分调参集与保留验证集，避免同义改写分别落入两组造成泄漏。数量以覆盖主要业务和失败类型为准，不沿用存在章节失配的历史清单直接计算准确率。

逐项对照：A 当前基线；B 正确性修复；C 混合召回；D 重排/上下文；E 树状路由。固定数据、模型和题目，分别记录收益与退化，不能同时修改全部变量后只报告最终分数。

| 指标 | 计算口径 | 初始建议门槛，尚未达成 |
| --- | --- | --- |
| 根路由集合准确率 | 实际分区集合与标注完全一致的案例占比，澄清单独统计 | ≥95% |
| 最终证据 Recall@5 | 每事项最终前五条中命中的黄金证据数 / 该事项黄金证据数，再宏平均 | ≥90%；多种等价证据预先标为替代组 |
| 树路径范围覆盖率 | 选定范围包含至少一组可回答证据的可回答事项占比 | ≥95%，并报告回退比例 |
| 无证据拒答率 | 无证据案例中未生成内部事实答案的占比 | ≥95% |
| 关键事实支持率 | 被人工判定由引用支持的关键事实数 / 输出关键事实总数 | ≥95%；金额、期限等另列错误数 |
| 部分证据处理 | 正确回答有证据事项且明确缺证事项 | 专项用例全部通过 |
| 分区隔离 | 出现禁止分区证据或查询 | 0 次 |
| 延迟 | 同硬件/负载下分阶段 p50/p95，记录冷暖启动 | 树化检索 p95 建议不超过修复后基线 1.5 倍；模型调用单列 |

门槛是首轮评审建议，不能视为对当前系统的质量承诺。小样本同时报告分子/分母与失败案例，不用一个百分比掩盖覆盖不足。树方案若只增加耗时而无召回收益，应保留为可关闭功能或推迟上线。

## 12. 决策建议与最终完成定义

建议先落实 P0–P2，使现有三分区系统具备可信的故障处理与诊断能力。主题分类方案明确后再进入 P4，P3 的质量基线用于判断 P5 树路由是否值得默认启用。当前不建议直接重建用户全部数据，也不建议用降低阈值作为通用修复。

采用的首版设计建议为：三个根分区保持稳定；每份文档唯一主题归属；父节点允许直接内容；物理索引按分区保留；逐层路由可在根分区内受控回退；版本发布采用明确写冻结窗口。以上是可评审的方案选择，尚不是已实施配置。

后续实施需要补齐的业务信息：代表性失败问题与预期证据、正式主题分类、跨主题文档处理约定、数据规模与可接受维护窗口。缺少这些信息不阻碍确定性缺陷修复，但会影响树分类和实际迁移。

只有满足以下条件，才可对外称“树状路由索引已完成”：

- [ ] 确定性检索缺陷已修复，定向测试通过。
- [ ] 节点结构可持久化，关系与分区约束可验证。
- [ ] 审核内容与节点归属一致，未审核内容不影响路由与回答。
- [ ] 查询确实按节点范围逐层执行，路径与回退可追踪。
- [ ] 召回、过滤、上下文和答案阶段均可定位失败原因。
- [ ] 版本构建、持久化回读、切换、中断恢复和回滚经过隔离演练。
- [ ] 在核验过的数据上完成获准范围内的质量对照，并报告退化案例。
- [ ] 前后端契约、历史兼容和现行功能文档同步完成。

在此之前，系统应继续描述为“三分区路由检索 MVP，树状路由优化规划中”。
